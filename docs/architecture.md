# 校园二手交易网站第一版技术架构

## 1. 架构目标

第一版采用**单体式全栈架构**：一个 Next.js 项目负责网页展示和服务端业务操作，PostgreSQL 保存结构化数据，对象存储保存商品图片。

这种结构适合 MVP：前后端集中在一个项目中，开发和部署路径较直接；以后规模或团队需要变化时，再评估是否拆分服务。

## 2. 技术选型

| 技术 | 在项目中的作用 | 选择理由 |
| --- | --- | --- |
| Next.js | 网页页面和服务端业务处理，例如读取商品、创建商品、管理收藏 | 前后端可放在一个项目里，页面和服务端逻辑之间调用直接，适合 MVP。 |
| TypeScript | 给代码中的数据、函数和组件标注类型 | 能较早发现字段拼错或数据类型不匹配的问题。 |
| Tailwind CSS | 编写页面样式 | 样式可以写在组件附近，方便快速搭建和调整页面。 |
| PostgreSQL | 保存用户、商品、图片记录和收藏 | 适合有关联的数据，并支持唯一约束、外键等规则来保护数据一致性。 |
| Prisma | 在 TypeScript 项目中读取和修改 PostgreSQL 数据 | 可从数据模型生成类型化的数据库访问接口，并提供迁移工具来管理表结构变化。 |
| Auth.js | 处理注册登录后的身份会话 | 与 Next.js 配合较自然，可通过安全的会话 Cookie 识别用户。第一版可采用账号密码登录，密码需单独使用安全哈希保存。 |

认证库的具体版本、适配器和配置，应在项目初始化时确认与所选 Next.js 版本兼容。第一版暂不接入校园统一认证或第三方登录。

## 3. 系统组成与数据流

```text
用户浏览器
   │ HTTPS 请求和页面
   ▼
Next.js
  ├─ 页面与交互
  ├─ 服务端业务操作、认证与权限检查
  ├─ Prisma ────────── PostgreSQL（用户、商品、收藏、图片记录）
  └─ 图片上传 ─────── 对象存储（图片文件）
```

浏览器通过 HTTPS 访问 Next.js。商品列表、商品详情和用户操作由 Next.js 服务端处理；服务端通过 Prisma 访问 PostgreSQL。图片文件放在对象存储中，数据库保存图片的存储键或地址、展示顺序等元数据，不把图片二进制内容存入数据库。

## 4. 核心数据表草案

具体字段、商品分类和成色规则需要结合产品决策再细化。

### 4.1 User（用户）

建议字段：

- `id`：唯一标识
- `email` 或其他登录标识：具体采用哪种待决定
- `passwordHash`：密码安全哈希，不能保存明文密码
- `displayName`：公开昵称
- `role`：普通用户或管理员
- `createdAt`：创建时间

手机号、学号等敏感信息只有确认业务确有必要后才加入。

### 4.2 Product（商品）

建议字段：

- `id`：唯一标识
- `sellerId`：发布者用户标识
- `title`、`description`：标题和描述
- `price`：价格，数据库类型应保证金额精度
- `category`、`condition`、`location`：分类、成色和交易地点
- `status`：至少包含在售和已下架
- `createdAt`、`updatedAt`：创建和更新时间

### 4.3 ProductImage（商品图片）

建议字段：

- `id`：唯一标识
- `productId`：所属商品
- `storageKey` 或 `url`：图片在对象存储中的位置引用
- `sortOrder`：详情页展示顺序
- `createdAt`：创建时间

图片文件本身由对象存储管理，数据库存储其引用。删除商品时需要一并清理图片记录，并按存储服务策略清理文件。

### 4.4 Favorite（收藏）

建议字段：

- `userId`：收藏用户
- `productId`：被收藏商品
- `createdAt`：收藏时间

对 `(userId, productId)` 设置联合唯一约束，避免同一用户重复收藏同一商品。

### 4.5 关系

- 一个用户可以发布多件商品；每件商品只有一个发布者。
- 一件商品可以有多张图片；每张图片属于一件商品。
- 用户和商品通过 Favorite 形成多对多收藏关系。
- 商品第一版至少有“在售”和“已下架”状态。是否增加待审核、已售出或违规隐藏等状态待产品确认。

## 5. 登录状态与认证

1. 用户提交账号和密码。
2. 服务端查找账号，并使用密码哈希验证密码；不能用明文密码比较或保存。
3. 登录成功后，认证方案建立会话。浏览器在后续请求中通过 Cookie 携带会话凭证。
4. Cookie 应设置 `HttpOnly`（网页脚本不能直接读取）、`Secure`（仅通过 HTTPS 发送）和合适的 `SameSite` 策略。
5. 服务端从有效会话识别当前用户；不能相信浏览器请求中自行提交的用户编号。
6. 用户退出时让会话失效或清除相应凭证。

还应对登录尝试做频率限制，并避免错误提示泄露过多账号状态信息。密码找回机制属于待决定事项。

## 6. 服务端操作与权限检查

创建、编辑、下架等写操作必须在服务端执行。推荐检查顺序：

1. 从有效会话取得当前用户；需要登录的操作若未登录则拒绝。
2. 校验请求字段，例如标题长度、价格范围、状态值和图片规则。
3. 查询目标商品，并确认商品存在。
4. 对普通用户，确认目标商品的 `sellerId` 等于当前用户 ID；管理员操作应单独检查管理员角色。
5. 执行数据库变更，并在成功时返回结果。

页面可以根据权限隐藏按钮，但这只改善界面体验；真正的授权检查必须在每次服务端操作时进行。更新时应只接受明确允许修改的字段，避免客户端传入 `sellerId` 或 `role` 等字段来提升权限。

## 7. 建议的项目目录

```text
校园二手平台/
├─ app/                    # Next.js 页面和服务端路由
│  ├─ (public)/            # 首页、搜索、商品详情、登录注册
│  ├─ account/             # 个人中心、我的商品、我的收藏
│  └─ api/                 # 需要提供 HTTP 接口时使用
├─ components/             # 可复用的页面组件
├─ lib/                    # 数据库、认证、验证和图片存储配置
├─ prisma/
│  ├─ schema.prisma        # 数据模型
│  └─ migrations/          # 数据库结构变更记录
├─ public/                 # 少量静态资源；不存放用户上传图片
├─ docs/                   # 项目文档
├─ .env.example            # 环境变量名称示例，不放真实密钥
├─ package.json
└─ tsconfig.json
```

具体路由目录可按创建项目时采用的 Next.js App Router 约定调整。

## 8. 本地开发环境

### 8.1 需要安装的软件

- Node.js 当前长期支持版本及 npm（通常随 Node.js 安装）
- Git
- PostgreSQL，或用于本地开发的 PostgreSQL 容器
- 代码编辑器，例如 VS Code

### 8.2 项目依赖类别

- Next.js、React、TypeScript
- Tailwind CSS
- Prisma CLI 和 Prisma Client
- Auth.js 的 Next.js 集成及所需认证适配器
- 服务端输入验证库，例如 Zod，用于校验表单和请求数据

图片存储 SDK、部署平台 CLI 等，应在选定服务后再添加。

## 9. 部署服务与配置

建议准备以下服务：

1. **Next.js 托管服务**：运行网页和服务端逻辑。
2. **托管 PostgreSQL**：保存用户、商品、收藏和图片元数据。
3. **对象存储**：保存上传图片；可选用与部署平台兼容的 S3 API 服务。
4. **域名与 HTTPS**：保护登录凭证和用户数据传输。

### 9.1 环境变量

环境变量放在本地 `.env.local` 或托管平台的密钥配置中，不提交真实值到 Git。可能需要：

```text
DATABASE_URL=...
AUTH_SECRET=...
AUTH_URL=...
图片存储服务地址、桶名、访问密钥等（依服务商要求配置）
```

实际变量名取决于 Auth.js 版本、托管平台和图片存储服务。`AUTH_SECRET` 和存储密钥应使用随机且保密的值，并仅由服务端读取。

### 9.2 部署配置要点

- 为生产环境单独配置数据库连接和对象存储凭证。
- 部署时执行 Prisma 数据库迁移，使数据库结构与代码版本一致。
- 配置生产域名和 HTTPS。
- 配置允许的图片格式、大小和数量，并按对象存储能力限制上传权限。
- `.env.example` 只列变量名称和说明，不包含任何实际密钥。

## 10. 第一版范围边界

第一版不实现：

- 站内聊天和消息通知
- 在线支付、平台担保、订单、退款
- 物流追踪
- 交易评价和信用分
- 个性化推荐、复杂搜索排序
- 多校区运营、校园统一身份认证
- 复杂运营分析后台

第一版聚焦注册登录、商品发布与管理、商品列表和关键词搜索、详情和收藏。筛选、举报审核等是否必须纳入 MVP，仍按需求文档中的待决定项确认。

## 11. 尚待确认的架构相关决策

- 登录标识使用邮箱、手机号还是其他形式，以及是否必须验证。
- Auth.js 的具体认证方式、适配器和数据库会话配置。
- 商品字段、价格规则、分类和成色取值。
- 图片服务商、图片数量和大小上限。
- 商品审核和举报流程是否属于第一版。
- 部署平台、服务区域、预算和预期用户规模。
- 用户联系方式是否公开，以及账号注销和数据保留规则。
